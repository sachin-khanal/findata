FINDATA - DEVELOPMENT SETUP
===========================

Written for: developers working on findata locally.
Project conventions (branches, changelog, dev tooling, running things): AGENTS.md.

Python environment, dependencies and commands are all managed by uv. You do not
need to create or activate a virtualenv by hand.


1. PREREQUISITES
----------------
- uv (https://docs.astral.sh/uv/). It installs Python 3.12 for you if needed.
- git
- Nothing else to install: SQLCipher (sqlcipher3) and keychain access (keyring) come as
  prebuilt wheels for macOS, Linux and Windows on x86-64 and arm64.
- Free Plaid Sandbox keys: https://dashboard.plaid.com/developers/keys
  (only needed to talk to Plaid; the test suite needs no keys or network)


2. FIRST-TIME SETUP
-------------------
  uv sync                      # creates .venv from pyproject.toml + uv.lock
  cp .env.example .env         # then edit .env, see section 3
  uv run findata init          # creates ~/.findata (see section 4)

Python version is pinned to 3.12 in .python-version (pyproject requires >=3.12).
Dependencies are locked in uv.lock. Do not edit it by hand; use "uv add <pkg>"
(runtime) or "uv add --dev <pkg>" (dev) and commit the updated lock file.


3. CONFIGURATION (.env)
-----------------------
Settings load from environment variables and an optional .env file in the
directory you run from. .env is git-ignored. Never commit it.

  PLAID_CLIENT_ID    from the Plaid dashboard
  PLAID_SECRET       from the Plaid dashboard (use the Sandbox secret)
  PLAID_ENV          sandbox (default) or production
  FINDATA_DATA_DIR   optional, default ~/.findata
  FINDATA_KEY_BACKEND  optional, auto (default), keychain or file (see section 4)
  FINDATA_HOST       optional, default 127.0.0.1; used by "findata serve web" only
  FINDATA_PORT       optional, default 8765; used by "findata serve web" only

The daemon starts without Plaid keys. Calls that need Plaid fail until they are
set. FINDATA_HOST must be a loopback address (127.0.0.1, ::1 or localhost):
"serve web" refuses any other host before it binds.
Only the daemon reads the Plaid keys. The CLI, "serve web" and "serve mcp" never
load them.


4. LOCAL DATA AND SECRETS (~/.findata)
--------------------------------------
  findata.db    SQLCipher-encrypted database (also encrypts its -wal/-shm files)
  master.key    master encryption key, ONLY when no OS keychain is available
                (otherwise the key lives in the OS keychain, one entry per data dir)
  credentials/  one file per role: web.token, cli.token, mcp.token (see section 5)
  daemon.sock   the daemon's Unix socket (only while it runs)
  daemon.lock, daemon.pid   one daemon per data directory (only while it runs)
  daemon.log    output of "findata start --background" (see section 5)

The data directory must be mode 0700 and the files 0600 (POSIX; on Windows the
per-user profile ACL applies). findata refuses to start if they are accessible to
others (fix with: chmod 700 <dir> / chmod 600 <file>).

The master key protects everything. If it is lost, the database cannot be
recovered, so back it up separately from the data. findata only ever creates a
new key when no database exists; with a database but no key it stops with an
error instead. Choose where the key lives with FINDATA_KEY_BACKEND:
auto (default: keychain, falling back to master.key), keychain, or file.
Design rationale: docs/adr/0002-layered-encryption-at-rest.md

Databases created before encryption was added are plaintext and are rejected;
delete the data directory and run "uv run findata init" again.

To start over with a clean slate, delete the whole directory (or point
FINDATA_DATA_DIR somewhere else) and run "uv run findata init" again.


5. PROCESS MODEL AND DAILY COMMANDS
-----------------------------------
findata is one daemon plus front ends:

  findata start     the daemon. The only process that holds the master key, opens
                    the database and talks to Plaid. Serves an API on the Unix
                    socket ~/.findata/daemon.sock (owner-only, no TCP).
  findata <cmd>     CLI commands (sync, txns, items, sandbox-link, status, stop,
                    grant, revoke, approve, audit) are clients of the daemon.
  findata serve web the web UI on 127.0.0.1:8765, a client of the daemon.
  findata serve mcp the MCP server on stdio for an agent, a client of the daemon.

Only "init" and "migrate" work without the daemon. "migrate" refuses while the daemon
runs (stop it with "findata stop" first): it holds the daemon's lock for the whole
migration, so a daemon cannot start halfway through either. "migrate --check" is
read-only and works either way. Everything else stops with
DAEMON_NOT_RUNNING when it is not running. Front ends never import the database,
key or Plaid code; tests/test_boundary.py fails if they do.

Run the daemon and the front ends in separate terminals:

  terminal 1:  uv run findata start            # foreground; Ctrl+C stops it
  terminal 2:  uv run findata sandbox-link     # link Plaid's test bank and sync it, no
                                               # browser; waits until history has loaded
                                               # (usually 10-30 seconds)
               uv run findata sync             # pull new/changed/removed transactions
               uv run findata txns             # print recent transactions
               uv run findata status           # daemon version, Plaid env, uptime
  terminal 3:  uv run findata serve web        # prints "Open findata: <link>"; open it
                                               # (--open does that for you)
  terminal 4:  uv run findata serve mcp        # normally started by an agent host

Background mode:
  uv run findata start --background   # returns once the daemon is ready
  uv run findata stop                 # stops it, background or not
Output of a background daemon is appended to ~/.findata/daemon.log (owner-only).
Read it when a start fails; the command also prints the last lines. Background
start is POSIX only (macOS, Linux). Add --wait-timeout <seconds> if the daemon
takes longer than 30 seconds to become ready.

Credentials. "findata init" (or the first "findata start") creates
~/.findata/credentials/<role>.token for each role, owner-only (0600). A client
reads only its own role's file:
  cli  and web   act for you (human)
  mcp            the agent: read-only unless you grant it writes
The daemon checks the role on every route and records every request in the audit
log ("uv run findata audit"). A leftover api.token file from older versions is
unused and can be deleted.

Grants and approvals. The agent cannot write until you allow it:
  uv run findata grant mcp-write --ops sync --for 15m   # --ops: sync, link,
                                                        # items.remove (comma-separated)
  uv run findata revoke mcp-write                       # end it now
  uv run findata approve <id>                           # allow one removal
Defaults: --ops sync, --for 15m; the longest grant is 24h. Grants expire on their
own and are cleared when the daemon stops. An agent removal also needs a fresh
approval each time. The web UI has an "Agent access" panel for the same actions.
On macOS the daemon asks for Touch ID (or the password) before a grant, an
approval, or a removal by cli/web; read the prompt. Where there is no such check
(Linux, Windows) web grants and approvals are refused: use the terminal.
Design and limits: docs/adr/0004-daemon-centred-architecture.md

Every command explains what it is doing and what to do next. For scripts, CI and
agents, add --json to sandbox-link, sync, txns or status (and grant, revoke, approve,
audit, items): output is one JSON object per line ("event": linking, linked,
waiting, poll, done, error, ...).

sandbox-link exit codes: 0 = history fully loaded, 2 = linked but Plaid was still
loading when the wait ended (nothing lost; run "findata sync" later, or raise
--timeout), 1 = error (bad keys, Plaid rejected the request, no credentials).
Plaid reports INITIAL_UPDATE_COMPLETE first, with few or no transactions; the rest
arrives as HISTORICAL_UPDATE_COMPLETE. "+0 new" with INITIAL_UPDATE_COMPLETE means
"not ready yet", not "no data".

The web API needs a browser session: open the "Open findata: <link>" line that
"findata serve web" prints. The link carries a one-time-per-run secret in its
fragment; restarting "serve web" ends all sessions, so open the new link. /api/health
works without a session.


6. TESTS AND LINTING
--------------------
  uv run pytest -q                   # tests use a fake Plaid gateway
  uv run pytest tests/test_boundary.py tests/test_daemon_e2e.py -v
                                     # the daemon boundary and the real-socket test
  uv run ruff check .                # lint
  uv run ruff format --check .       # formatting (drop --check to fix)

Optional pre-commit hooks (ruff, private-key detection, large-file check,
whitespace fixes):
  uvx pre-commit install

CI (.github/workflows/ci.yml) runs "uv sync --locked", ruff check, ruff format
--check and pytest on pushes to main and on pull requests. Run the same four
commands locally before opening a PR.


7. CODE LAYOUT
--------------
  src/findata/daemon/            the daemon: server.py (findata start), app and routes,
                                 auth (credentials), grants, presence (Touch ID),
                                 audit, events, jobs, lock, scheduler
  src/findata/client/            DaemonClient, the only way front ends reach data
  src/findata/web/               web front end (app.py, session.py, index.html)
  src/findata/mcp/server.py      MCP front end
  src/findata/cli/               "findata" command; commands/ has one file per group
  src/findata/wire.py            request/response shapes shared by daemon and clients
  src/findata/locations.py       where files in the data directory live
  src/findata/config.py          settings (daemon only)
  src/findata/security/          master key, key derivation, AES-GCM field encryption
  src/findata/db.py              SQLAlchemy models and engine
  src/findata/plaid_gateway.py   the only module that imports plaid-python
  src/findata/sync.py            cursor-based transactions sync
  tests/                         pytest suite (conftest.py has the fake gateway)

Core modules (db, security, plaid_gateway, sync, linking, waiting, queries, schema,
runtime, contexts, config) are imported only by the daemon, plus init and migrate.
tests/test_daemon_e2e.py runs a real daemon on a real socket with the fake gateway.
Tests that bind a Unix socket use a short directory under /tmp: macOS limits socket
paths to about 104 bytes.


7b. KNOWN ISSUE: .venv GETS HIDDEN ON macOS (iCloud/Google Drive Desktop folders)
---------------------------------------------------------------------------------
If the project lives under ~/Desktop or ~/Documents and those are synced, macOS marks
dot-prefixed entries (.venv, .git, ...) and everything inside them with the "hidden" flag
(check with: stat -f '%Sf' .venv). Python skips hidden .pth files, so the editable install
breaks with "ModuleNotFoundError: No module named 'findata'" or uv reports the venv invalid.
Fix once: keep the venv outside the synced folder, e.g. in ~/.zshrc
    export UV_PROJECT_ENVIRONMENT="$HOME/.venvs/findata"
or move the checkout to an unsynced path like ~/code/findata. Quick repair in place:
    chflags -R nohidden .venv

8. SCHEMA MIGRATIONS
--------------------
The schema is versioned with Alembic (scripts in src/findata/migrations/versions). You never
call the alembic CLI: the database is SQLCipher-encrypted, so everything goes through findata.

  uv run findata migrate           # apply pending migrations (copies the DB file first)
  uv run findata migrate --check   # exit 1 if the schema is behind; changes nothing

  * migrate refuses (exit 1, DAEMON_RUNNING) while the daemon runs; run `findata stop` first.
  * A brand-new database is created at the latest version (`findata init` does this).
  * A database from before migrations existed is adopted as version 0001, data untouched.
  * A database that is behind is never changed implicitly: every other command stops and
    tells you to run `findata migrate`. The pre-migration copy is
    ~/.findata/findata.db.bak-<timestamp> (owner-only); delete old ones once you are happy.
  * There is no `downgrade` command: restore the backup copy instead.

Changing the schema: edit the model in src/findata/db.py, then add the next file under
src/findata/migrations/versions by hand (copy 0001's header; revision "0002", down_revision
"0001"; use op.batch_alter_table for ALTERs). tests/test_schema.py fails if the models and
the migrations disagree, so a forgotten migration is caught in CI.
